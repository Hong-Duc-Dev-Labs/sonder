# Phase 5: DSD playback

## Overview

Read DSF and DFF (DSDIFF, uncompressed; DST-compressed is out of scope), then play DSD as
DoP on capable DACs or convert DSD→PCM for everything else.

## Key Insights

- DSF stores per-channel blocks of 4096 bytes, LSB-first bit order; DFF stores interleaved
  bytes, MSB-first. Normalise to an internal MSB-first interleaved byte stream.
- DoP: 16 DSD bits per channel per PCM frame in a 24-bit word with alternating markers
  0x05/0xFA; carrier rate = DSD rate / 16 (DSD64 → 176.4 kHz, DSD128 → 352.8 kHz,
  DSD256 → 705.6 kHz). Must be sent bit-perfect: volume and DSP must be bypassed.
- Native DSD on Windows generally needs ASIO (deferred); on Linux ALSA exposes
  `DSD_U32_BE` on some DACs — support it if the device advertises it.
- DSD→PCM: decimating low-pass FIR from the 1-bit stream (e.g. DSD64 → 352.8 kHz then
  further), built on phase 6's FIR core and Sonder filter design (no second filter
  engine); its output may then pass through the normal SRC. Roon's 5 algorithms are a
  reference for options only.
- DoP silence: on underrun, pause and stop the backend must write DoP idle frames
  (0x69 DSD silence with correctly alternating 0x05/0xFA markers, continuing the packer's
  marker phase) instead of zeros, otherwise the DAC leaves DSD mode with a loud pop.
  Pause/stop fade to DoP silence before the stream stops.

## Implementation Steps

1. DSF/DFF readers with unit tests on generated byte patterns (bit order, block layout).
2. DoP packer + unit tests (marker alternation, byte placement, continuity across buffers and tracks).
3. Engine DSD path; NullBackend test asserts DoP frames decode back to the original DSD bytes.
4. DSD→PCM decimation filter design (Sonder-owned coefficients generated by a build-time script) + frequency-response test.
5. Manual test: DoP on a DoP DAC (DAC shows DSD), PCM fallback on another device.

**Implementation note.** The DoP marker phase lives in the output renderer, the only writer of
device bytes: `sonder-engine::dop::Packer` produces marker-free payload and the renderer
inserts 0x05/0xFA and emits 0x69 0x69 idle frames with the same alternation. A packer that
stamped markers ahead of playback could not stay in phase when a pause or underrun inserted
an arbitrary number of idle frames.

**Choosing the DSD mode while the device is busy.** The next track (gapless prefetch, seek,
volume restart) is chosen while our own stream still holds the device, and ALSA `hw:` probes
then fail with EBUSY. An open DSD stream at the needed rate is reused without probing; a
probe error other than "unsupported format" counts as unknown, the requested mode is assumed,
and if the device rejects it once free the track is decoded again (once) to fall back
correctly. `NullBackend::with_busy_probes` reproduces this in tests.

**Stop.** ALSA drops queued audio, then plays one period of DSD idle before closing; WASAPI
answers the next device periods with idle before stopping; CoreAudio switches the IOProc to
idle-only for two cycles. Hardware verification is still part of the manual DAC test.

**Settings.** The DSD mode (per device) and the DSD→PCM rate are user settings: the app stores
them in `settings.toml` (`dsdModes`, `dsdPcmRate`) and applies changes live through
`Player::set_dsd`, which restarts a playing DSD track from its position; the CLI takes
`--dsd-mode` and `--dsd-pcm-rate`.

**Phase 6 interaction.** Phase 5 had to ship DSD→PCM before phase 6's shared FIR core existed,
so `sonder-dsp` carries its own two decimator stages (`build.rs` tables). Phase 6 should port
`dsd2pcm` onto `FirCore` rather than letting a second filter engine grow.

## Success Criteria

- Round-trip test: DoP-unpacked output == source DSD bytes.
- DAC displays DSD64/DSD128 when playing DSF and DFF via DoP.
- DSD→PCM output of a DSD-encoded 1 kHz tone shows the tone with noise shaped above 20 kHz attenuated per the filter spec.

## Risk Assessment

- DoP requires untouched 24-bit words; any stage left enabled corrupts it. Engine refuses to start DoP with active PCM stages and reports why.

## Security Considerations

- Validate chunk sizes in DFF/DSF headers before allocation (no unbounded allocs from untrusted headers).
