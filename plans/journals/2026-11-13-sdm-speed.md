# SDM speed

## What happened

The plan assumed DSD256/order 7 ran at 1.19 s per second of audio. The first baseline gave
344 ms. A third run gave 1.1 s with the same binary. Pinning showed why: on this i5-12450HX
the modulator takes 450 ms on a P-core and 869 ms on an E-core, and unpinned runs flip
between a fast and a slow state. The documented 1.19 s was a slow-state run. The E-core
figure became the target to beat, because Windows can park a background app's threads there.

The new loop keeps each channel's state in locals for the block, makes the order a const
generic over zero-padded coefficient arrays, stores the interpolator history twice so the
window needs no modulo, builds each output byte in a register and runs channels in
interleaved pairs. Results for DSD256/7: 225 ms P-core, 318 ms E-core, 174–379 ms unpinned.

## Decisions

- Kept the per-bit stability check so the output stays byte-identical; folded it into one
  `!(abs <= limit)` per state, which also catches NaN.
- Proved equality against a test copy of the old loop. Clamped input never trips the reset,
  so the test injects NaN and near-limit state mid-stream and asserts that every case reset.
- No threads (approach B): not needed.

## Found along the way

- `benches/resampler.rs` measures 44.1k → 11.29 MHz, but the engine resamples only to
  `DSD rate / 8`. Added `pcm_to_dsd/*` to `benches/sdm.rs` for the real path. DSD256/7 takes
  371 ms on a P-core, 632 ms on an E-core and 705 ms unpinned in the slow state. The
  resampler now costs more than the modulator.
- Benchmarks on this laptop need pinning or several runs; a single unpinned number is not
  evidence.
